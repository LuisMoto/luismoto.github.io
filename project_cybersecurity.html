Planteamiento del Problema

Como proyecto final de la materia Introducción a Redes Neuronales (UNAM, 2026), se desarrolló una red neuronal capaz de clasificar correos electrónicos en tres categorías: Seguro (0), Phishing (1) e Inyección SQL (2). El modelo procesa simultáneamente la secuencia de texto y un vector de características estructurales extraídas manualmente, alcanzando una precisión del 99.37% en el conjunto de prueba.

Muestreo y Data Augmentation

Se utilizó submuestreo (undersampling) para balancear el corpus a 11,340 muestras por clase. Durante las pruebas de inferencia — no en el diseño inicial — se identificó que el modelo asociaba el idioma español con la clase "Segura", ya que los datasets de phishing disponibles estaban en inglés. Para corregir este sesgo, se aplicó Data Augmentation inyectando muestras sintéticas de phishing en español (con y sin enlaces), lo que generó una iteración adicional completa del pipeline de datos y reentrenamiento.

Topología de la Red (Doble Entrada)

El modelo implementa una arquitectura de doble entrada en Keras que combina un bloque Transformer para procesamiento de texto con una red densa para características de dominio extraídas manualmente.

Rama NLP (Transformer)

Una capa de Embedding entrenada desde cero, conectada a un bloque de Multi-Head Attention, permite al modelo capturar el contexto semántico sin depender de modelos preentrenados. Se eligió entrenar el Embedding propio en lugar de usar modelos como RoBERTa o BERT porque estos están optimizados para lenguaje natural humano e ignoran caracteres especiales como comillas simples, asteriscos o guiones dobles, que son precisamente la sintaxis que distingue una inyección SQL de texto ordinario.

Extracción y MaxPooling

Se reemplazó GlobalAveragePooling1D por GlobalMaxPooling1D para evitar que ataques cortos de inyección SQL se diluyan matemáticamente dentro de textos conversacionales largos. El promedio atenuaba el valor de tokens de ataque; el máximo preserva el pico de activación más alto de la secuencia.

Regularización y Optimización

Entrenado con optimizador Adam (lr=0.001) y función de pérdida sparse_categorical_crossentropy. Se aplicaron capas Dropout (0.1 y 0.2), BatchNormalization y los callbacks EarlyStopping, ReduceLROnPlateau y ModelCheckpoint para controlar el overfitting y guardar únicamente el mejor modelo.

Decisiones de Implementación

Las siguientes decisiones fueron tomadas durante el desarrollo iterativo del proyecto. Cada una resolvió un problema concreto identificado en las pruebas.

1. GlobalMaxPooling1D en lugar de GlobalAveragePooling1D

Cuando un ataque SQLi aparece en un correo conversacional largo (ej. "Creo que encontré un bug, si escribo admin' OR 1=1 -- el sistema me deja entrar"), el promedio de los 40+ tokens inofensivos diluía el valor del token de ataque a casi cero. Al usar MaxPooling, el modelo toma el valor máximo por dimensión del embedding, preservando la señal más fuerte sin importar dónde aparezca en la secuencia.

# Rama de NLP (Transformer) - Sustitución del pooling
# text_vec = layers.GlobalAveragePooling1D()(seq_out)
text_vec = layers.GlobalMaxPooling1D()(seq_out)
text_dense = layers.Dense(16, activation="relu")(text_vec)

2. Arquitectura de doble entrada para conectar features.py al modelo

En la versión original, features.py existía pero nunca se llamaba desde trainer.py ni desde inference_engine.py. El modelo de entrada única ignoraba por completo las 14 características manuales. Al agregar un segundo Input y concatenar ambas ramas antes del clasificador final, las features de dominio (URLs sospechosas, tokens SQLi, densidad de vocabulario de phishing) se integran al proceso de decisión.

# Rama 2: Características extraídas manualmente
feat_input = Input(shape=(N_FEATURES,), name="feat_input")
feat_out = layers.Dense(16, activation="relu")(feat_input)

# Fusión de ramas y clasificador
concat = layers.Concatenate()([text_dense, feat_out])
outputs = layers.Dense(3, activation="softmax")(concat)

3. Tokenización estructural de URLs en lugar de eliminarlas

Eliminar URLs del texto perdía información crítica. En cambio, preprocessing.py analiza la estructura de cada URL y la reemplaza por un token semántico que el modelo aprende a interpretar. Dominios de confianza como github.com generan url_safe_domain, mientras que IPs directas generan url_ip_detected. Esto permite que el modelo distinga entre un enlace de GitHub legítimo y un enlace de phishing con dominio sospechoso.

if is_safe_domain(domain):
    text = text.replace(url, " url_safe_domain ")
elif re.match(r"^\d{1,3}(\.\d{1,3}){3}$", domain):
    text = text.replace(url, " url_ip_detected ")
else:
    text = text.replace(url, " url_suspicious_tld ")

4. Corrección del regex de URLs

El regex original http\S+ solo capturaba URLs con protocolo explícito. La mayoría de los correos de phishing reales usan URLs como www.banco-seguro.xyz/login o dominios directos sin http://, por lo que pasaban sin tokenizarse y el modelo las leía como texto ordinario. El regex corregido cubre las tres formas más comunes de URL en correos electrónicos.

# Expresión regular actualizada para capturar variaciones
url_pattern = re.compile(
    r"(https?://\S+|www\.\S+|\b(?:\w+\.)+[a-zA-Z]{2,}\b(?:/\S*)?)"
)
urls_found = url_pattern.findall(text)

Análisis de Falsos Positivos

Durante la inferencia, se observó que el modelo desarrolló sensibilidad hacia vocabulario como "urgente" o "password". Un ataque de Inyección SQL camuflado dentro de un texto con lenguaje de ingeniería social puede clasificarse incorrectamente como Phishing, ya que el peso acumulado de las palabras de alerta en la capa de atención supera el valor del token SQLi en el MaxPooling. Este comportamiento revela cómo interactúan ambas ramas del modelo en casos límite.

Conclusiones del Proyecto

El desarrollo del sistema mostró que una arquitectura de doble entrada es viable para clasificación multiclase en ciberseguridad:

  • El uso de callbacks evitó el sobreajuste en épocas avanzadas sin necesidad de intervención manual.
  • Una arquitectura entrenada desde cero resultó más adecuada que Transfer Learning para detectar sintaxis específica como comandos SQL y patrones de URL. Modelos como RoBERTa o XLM-RoBERTa, aunque más potentes en tareas de lenguaje natural general, no están diseñados para preservar la semántica de caracteres especiales que son centrales en la detección de inyecciones SQL.
  • La generación de datos sintéticos demostró ser una alternativa viable para corregir sesgos de recolección cuando no se dispone de datasets balanceados en el idioma requerido.
  • Trabajo futuro: Como trabajo futuro, podría plantearse la incorporación de un corpus de phishing en español de fuente real, la evaluación del modelo contra técnicas de evasión adversarial, y la exploración de arquitecturas multilingües que equilibren la comprensión de lenguaje natural con la detección de sintaxis específica de ataque.
